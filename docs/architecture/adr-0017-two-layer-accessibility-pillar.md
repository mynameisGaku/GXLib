## Context

### Problem Statement
GXLib's identity, as stated by the project owner, has two distinct user audiences whose needs are usually treated as opposing:

1. **Layer 1 — Beginner-usable.** A C++ beginner (e.g., someone graduating from DXLib) must be able to draw a sprite, play a sound, and read input within minutes of opening the repo. Failure modes must be discoverable, defaults must be sensible, and the public surface must not require knowledge of DX12, ECS, FrameGraph, or any other engine internal.

2. **Layer 2 — Core-modifiable.** A user who has graduated from Layer 1 and become curious about how rendering / audio / physics actually work must be able to reach in and modify the core. They should be able to add a custom render pass, swap in a custom shader, write a new MaterialDomain, or replace the SceneRenderer — without forking the engine or modifying `detail::`-locked code.

Most engines pick one: hobby engines aim Layer 1 only (no Layer 2); pro engines aim Layer 2 only (no Layer 1). GXLib commits to **both, with a continuous slope between them** — no cliff where the user has to re-learn everything.

### Constraints
- The Layer 1 surface (DXLib Compat, `gx::App`) must not leak DX12 / DXGI / archetype / Lua-state types (per existing forbidden patterns)
- The Layer 2 surface (FrameGraph passes, ShaderLibrary, MaterialDomain, SceneRenderer) must be **public, headers-installed, Doxygen-documented, and have at least one in-repo example** of extension
- Extension points must not be `detail::`-namespaced or `friend`-locked
- Both layers must coexist in the same process — Layer 2 modifications must not break Layer 1 callers

### Requirements
- Define what "Layer 1 ready" means concretely (testable)
- Define what "Layer 2 ready" means concretely (testable)
- Bind these as forbidden_patterns in the architecture registry so future ADRs and code review reject violations
- Provide a path: Layer 1 → middle (`gx::App` class API, ECS, AssetDatabase) → Layer 2 (FrameGraph, GraphicsDevice, custom shaders) without an arbitrary discontinuity

## Decision

**GXLib commits to a Two-Layer Accessibility Pillar. Every public-facing API decision MUST satisfy both layers' constraints. The pillar is enforced via four new forbidden_patterns + one architectural api_decision in the registry, and via a per-PR review checklist embedded in `docs/CLAUDE.md`.**

Concrete rules:

### Layer 1 — Beginner-Usable (testable definitions)

A feature is **Layer 1 ready** when ALL of the following are true:

- **L1.1** The DXLib-shaped procedural call exists in `gx::` namespace (e.g., `gx::DrawGraph`, `gx::PlaySoundMem`) OR the corresponding `gx::App` method exists with a 1-line example.
- **L1.2** Sensible defaults: calling the API with minimal arguments produces a reasonable result. No "you must initialize X first" gotchas hidden in the docs.
- **L1.3** Failure paths return DXLib-style int return codes (0 success, -1 failure) AND log a human-readable error via `gx::Logger`. Silent failure is forbidden.
- **L1.4** The Doxygen `///` comment on the public function explains: what it does, what it returns on success/failure, one example use. Japanese is acceptable; English is preferred for the procedural surface; comments must not be empty or autogenerated boilerplate.
- **L1.5** A minimal usage example exists somewhere reachable: `template/main.cpp`, `sdk/template/main.cpp`, `examples/`, or in the Doxygen comment itself.

### Layer 2 — Core-Modifiable (testable definitions)

A subsystem is **Layer 2 ready** when ALL of the following are true:

- **L2.1** Extension points are PUBLIC headers, not `detail::` / private / friend-locked. A user can `#include <GXLib/Subsystem/ExtensionPoint.h>` and derive / instantiate without modifying engine source.
- **L2.2** At least one in-repo example demonstrates the extension. For Graphics this means: a sample custom render pass added to FrameGraph; a sample custom shader registered with ShaderLibrary; a sample new MaterialDomain.
- **L2.3** The extension point has Doxygen `///` documentation explaining the contract (what to override, what invariants to maintain, what threading model applies, what FrameGraph / Job System integration is expected).
- **L2.4** Internal types the extension point depends on (e.g., `gx::CommandList`, `gx::FrameGraph::Pass`) are themselves public headers — Layer 2 cannot have a transitive `detail::` dependency.
- **L2.5** Modifying the extension does NOT require recompiling the engine library. Subclasses, FrameGraph pass registrations, and shader additions all work as application-side code linked against `libGXLib`.

### New Forbidden Patterns (registered in `docs/registry/architecture.yaml`)

1. **`internal_only_extension_point`** — Any extension point intended for Layer 2 users (custom render pass, custom shader, custom MaterialDomain, custom audio DSP effect, custom asset provider, custom physics shape, custom widget) must NOT live under `detail::` namespace, in a `*_internal.h` header, or behind a `friend class` declaration. If it's an extension point, it's public.

2. **`undocumented_layer1_api`** — Public functions in `gx::` namespace exposed via Compat layer (Compat_*.cpp) MUST have a Doxygen `///` block with at least: brief description, return value semantics, one usage example. Empty or single-line comments are forbidden on this surface.

3. **`silent_failure_in_compat_layer`** — Compat layer functions returning int MUST return -1 on failure AND log an error via `gx::Logger`. Returning -1 silently (no log) hides bugs from Layer 1 users who can't diagnose engine internals. Functions returning void on a failure path must log.

4. **`layer1_breaking_change_without_compat_shim`** — Renaming, removing, or changing the signature of a Layer 1 procedural function (anything in `gx::` Compat layer that mirrors a DXLib name) requires either (a) keeping the old function as a thin shim with `[[deprecated]]` attribute, or (b) a major version bump documented in CHANGELOG with a migration table. Layer 1 stability is the SDK's selling point.

### New API Decision (registered)

- **`two_layer_accessibility_pillar`** — Every public API addition is reviewed against L1.1–L1.5 and L2.1–L2.5. Subsystems are scored periodically (per release) and gaps flagged for follow-up. The pillar takes precedence over implementation convenience.

### Per-PR Review Checklist (embedded in `docs/CLAUDE.md`)

For any change touching public API (`GXLib/**/*.h` headers exposed in `sdk/include/`):

```
[ ] L1: Does the new API have a DXLib-shaped procedural form in gx:: OR a gx::App method?
[ ] L1: Sensible defaults — works with minimal args?
[ ] L1: Failure path returns -1 + logs?
[ ] L1: Doxygen comment with example?
[ ] L1: Minimal usage example exists somewhere?
[ ] L2: If this is an extension point — is it in a public header, not detail::?
[ ] L2: At least one in-repo sample uses the extension?
[ ] L2: Doxygen explains the override contract + threading + integration?
[ ] L2: Modification works as application-side code (no engine recompile)?
```

### Architecture Diagram

```
Layer 1 surface (beginner-usable):
   gx::DrawGraph(), gx::PlaySoundMem(), gx::CheckHitKey()      ← Compat (procedural)
   gx::App with virtual OnUpdate / OnRender / OnInit            ← class-style (still beginner)
   Sensible defaults + DXLib-shaped error codes + Logger        ← failure mode
        │
        │  curiosity / growth path
        ▼
Middle layer (intermediate):
   gx::AudioManager, gx::AssetDatabase, gx::ECS::World          ← engine subsystems
   gx::Animator, gx::PhysicsWorld3D, gx::InputManager           ← typed APIs
   AssetHandle<T>, EntityHandle, opaque resource handles        ← safe references
        │
        │  ready to modify the core
        ▼
Layer 2 surface (core-modifiable):
   gx::FrameGraph::Pass — declare custom render pass            ← custom rendering
   gx::ShaderLibrary::Register — add a HLSL shader               ← custom shader
   gx::MaterialDomain extension — new GBuffer-compatible mat'l   ← custom material
   gx::AudioDSP::RegisterEffect<T> — new DSP effect              ← custom audio FX
   gx::AssetDatabase::RegisterType<T> — new asset type           ← custom asset
   IFileProvider implementation — new IO backend                 ← custom IO
   Custom physics shape via PhysicsShape interface               ← custom collision
   Custom widget deriving gx::GUI::Widget                        ← custom UI
       │
       └── All public, Doxygen-documented, in-repo examples, no detail::

Forbidden:
   ✗ Extension point hidden in detail::
   ✗ Layer 1 function with empty Doxygen
   ✗ Compat function returning -1 silently
   ✗ Renaming gx::DrawGraph without a shim
```

## Alternatives Considered

### Alternative 1: Layer 1 only (DXLib-clone)
- **Description**: Treat GXLib as a DXLib successor; advanced features hidden behind walls
- **Pros**: Simpler scope; smaller public surface
- **Cons**: Loses the second audience (curious users who would graduate to engine modification); relegates GXLib to "DXLib but newer"
- **Rejection Reason**: Project owner explicitly wants Layer 2 access. Layer 1 only forecloses growth.

### Alternative 2: Layer 2 only (pro engine)
- **Description**: Drop the Compat / DXLib-shaped surface; expect users to understand DX12, ECS, FrameGraph
- **Pros**: Cleaner internal architecture without back-compat baggage
- **Cons**: Throws away the entire DXLib-graduating-developer audience, who are exactly who GXLib is meant for. ADR-0003 already commits the opposite direction.
- **Rejection Reason**: Contradicts ADR-0003 and the project's identity. Beginner accessibility is non-negotiable.

### Alternative 3: Pillar as soft guideline (no forbidden_patterns)
- **Description**: Document the two-layer goal in prose only; don't bind it as registry-enforced rules
- **Pros**: Less ceremony per PR
- **Cons**: Soft guidelines drift. Without forbidden_patterns, future ADRs can quietly violate the pillar (e.g., "this extension point is only for advanced users, let's put it in detail::"). The whole point of the registry is to make architectural commitments mechanically enforceable.
- **Rejection Reason**: Half-measure. Either commit and enforce, or don't commit.

## Consequences

### Positive
- Identity clarified: GXLib is a "two-layer SDK", not just another engine or another DXLib clone
- Future ADRs and PRs have a concrete checklist — no more "is this a beginner concern?" arguments
- Existing ADRs (0008 FrameGraph, 0009 PhysicsShape, 0010 AudioDSP, 0007 IFileProvider, 0012 Widget) already contain Layer 2-shaped extension points; this pillar formalises and protects them
- DXLib-graduating users have a documented growth path instead of hitting a wall

### Negative
- Per-PR overhead: 9-item checklist for any public API change
- Some current code likely violates the pillar (TODO list will surface them — see Step 2 source analysis)
- Layer 1 surface stability commitment means painful deprecation cycles instead of clean renames
- Doxygen-with-examples discipline is real authoring work

### Risks
- **Pillar bit-rot** if reviewers don't enforce the checklist. *Mitigation*: per-release audit (Layer 1 / Layer 2 score per subsystem); flag regressions.
- **Layer 2 examples become test debt** if they're not actually maintained. *Mitigation*: examples live under `examples/` and are built by CI; broken examples = broken build.
- **Layer 1 stability locks in early mistakes**. *Mitigation*: shim + deprecate is the documented escape — bad APIs don't get removed, they get wrapped.

## Validation Criteria

- **Layer 1 smoke test**: a fresh dev clones the repo, opens `template/main.cpp`, follows the README, and has a window with a sprite drawn within 5 minutes. No "wait, I need to install X" interruptions.
- **Layer 2 smoke test**: a Layer-1-comfortable user wants to add a custom bloom variant. They can: read the FrameGraph public header, find the example custom-pass under `examples/`, copy and modify it, rebuild only their app (not the engine), and see their custom bloom on screen. No engine source modification required.
- **Compat layer audit**: 100% of `gx::` Compat functions have non-empty Doxygen blocks; sampled 20 functions for example presence — at least 80% have an example.
- **Extension point audit**: 0 instances of `detail::`-namespaced extension points; 0 instances of `friend class` declarations creating Layer 2 access requirements.
- **Failure mode audit**: sampled 20 Compat functions returning int; 100% of failure paths log via `gx::Logger`.
